# 空间 Job 与 Harbor Agent 评测需求基线

> 状态：Implemented Reference。2026-09-08 经需求讨论确认并先于实现落地，作为本次实现和验收依据。可执行契约与首版边界见 [空间 Job API](workspace-jobs-api.md)；此基线不扩张实现文档列出的框架支持范围。

## 目标与边界

用户在所属空间中提交一次性 Job。普通命令任务与 Agent 能力评测属于同一套任务生命周期，通过 `type` 区分为 `command` 和 `agent_evaluation`。平台生成唯一 `taskId`；独立 Job 不要求 `appId`，不创建占位 Application 或 Component。

复用现有 WorkflowQueue、JobInfo、调度、执行租约和取消机制。业务类型描述任务目的，执行框架描述评测方式；两者不混用。首版只接入 Harbor，后续框架通过评测规格扩展，不为每个框架增加 Trait 或平行调度器。

首版范围为后端 API、持久化、Kubernetes 执行、结果访问和保存。无需前端页面、人工作品审核流程、平台镜像构建或新的客户端 CLI。发布为新的实现 PR，原设计 PR 不作为实现完成的证据。

## 用户流程

1. 管理员预配置数据库及 MinIO 存储连接。用户注册后获得与所属空间权限一致的存储使用能力；连接凭据不交给用户。
2. 用户上传包含题目、输入文件、任务环境定义和判定规则的原生 Harbor 任务包。任务包可复用，平台记录其内容摘要与空间归属。
3. 用户在本地构建任务环境镜像并推送到集群可访问的仓库。任务包引用已构建镜像；平台不执行 Dockerfile 构建。
4. 用户选择 Harbor 已适配的 Agent、模型和凭据，提交 `agent_evaluation` Job，指定任务包、运行资源、结果保存目标及策略。
5. 平台运行 Harbor，由 Harbor 驱动 Agent 执行任务并调用用户提供的 verifier，采集框架产生的全部数据。
6. 评测执行结束后，平台自动启动结果保存。用户分别查看执行状态及各目标的保存状态，并下载被授权的数据。
7. 保存失败时可单独重试保存，复用已有原始结果，不再次调用 Agent 或重新测评。

## Job 规格

公共字段承载名称、类型与空间归属。`spec` 承载类型专属业务输入，`traits` 只描述已有资源、挂载、环境和安全等运行能力。

| 维度 | `command` | `agent_evaluation` |
| --- | --- | --- |
| 业务输入 | 容器镜像与命令 | 框架、任务包、Agent、模型、框架运行参数 |
| 框架 | 无 | 首版 Harbor，固定受支持版本 |
| 身份 | 平台生成 TaskID，所属空间 namespace | 同左 |
| 应用关联 | 不需要 AppID | 不需要 AppID |
| 执行 | 复用一次性 Kubernetes Job 生命周期 | Harbor Runner 驱动任务环境并执行评测 |

API 应拒绝不支持的类型、框架、参数及不完整输入。框架参数不可覆盖平台决定的 namespace、ServiceAccount、权限、结果上报地址或执行身份。凭据使用所属空间的 Secret 引用；平台只持久化引用，不主动将凭据明文写入请求快照或摘要。框架和任务日志按原样保留。

## Harbor 输入与执行

采用 Harbor 原生任务格式，而非平台另造题目或评分格式。任务目录包括 `instruction.md`、`task.toml`、环境定义、`tests/test.sh` 和可选的解题参考及输入文件。用户维护 verifier；平台不替用户定义“PPT 是否完整”等业务评分标准。

Agent 由 Harbor 现有适配器运行。首版不要求用户提供任意 Agent 服务协议，也不假定任意上传的 Agent 镜像能被自动调用。用户本地构建的是任务环境镜像，Agent 名称、模型及所需环境凭据作为独立输入。

Harbor Runner 与它启动的任务环境均位于任务所属空间。具体容器或 Pod 划分取决于受支持的 Harbor 后端；不要求将所有执行放在同一个 Pod。任务环境使用预构建镜像，必须遵守空间安全策略与资源约束。取消、超时与恢复执行需要清理所属任务资源，并保留已经收集的数据。

任务包上传和解包应限制大小，拒绝路径逃逸、危险链接及重复歧义条目；输入内容摘要用于保证复用时执行的是已提交内容。框架进程退出码与框架原生结果共同说明执行结果，不能把“进程退出 0”一概当成所有试验成功。

## 输出与数据保存

用户需要框架产生的全部数据，包括聚合结果、各 trial 结果、奖励值、轨迹、日志、产物和框架附带文件。平台可提供摘要帮助查询，但不可用摘要替代完整原始文件；文件内容保持原样。

区分三个概念：评测执行、平台持有的原始结果、用户选择的保存副本。

| 保存方式 | 行为 |
| --- | --- |
| MinIO | 保存完整结果文件及定位信息 |
| 数据库完整模式 | 保存元数据与完整文件内容 |
| 数据库元数据模式 | 只保存清单、摘要、状态和文件引用；必须同时选择 MinIO 保存完整文件 |

用户可通过策略选择一个或多个已授权目标。每个目标独立记录状态、错误和重试结果。一个目标成功、另一个失败时，明确展示各自结果并保留成功副本；不得把全部结果回滚，也不得把整个评测改为执行失败。

保存自动触发。手动重试以平台已保存的原始数据为来源，并需要处理重复请求，避免重复生成不可追踪副本。数据库元数据模式必须能定位同次结果的完整 MinIO 副本；MinIO 尚未成功时不能声称完整结果已经可用。

## 权限与策略

复用现有注册、个人/团队空间和成员授权。上传任务包、提交 Job、读取或下载结果、选择目标、修改策略和重试保存均校验当前空间权限。知道 TaskID、任务包 ID 或文件路径不能获得跨空间访问权。

管理员维护存储连接，用户仅能在已提供的能力中选择策略。注册初始化赋予存储使用能力，不创建 Kubernetes 资源。团队空间沿用成员权限，不增加平行账号或权限系统。

平台原始结果默认保留 **90 天**，用户可修改保留策略。到期删除仅作用于平台持有的原始结果，**不删除已经保存到用户所选目标的副本**。原始结果过期后，尚未成功的目标无法再从该来源重试，API 应明确说明；已有成功副本仍可依其访问策略读取。可复用任务包不因某次评测结果到期而被一并删除。

## 状态与可靠性

评测状态回答“Agent 与评测框架是否执行完成”；保存状态回答“输出是否已保存到每个目标”。两种状态分别呈现。

执行沿用现有排队、运行、成功、失败、取消、超时及租约恢复语义。保存至少能表达等待、进行中、成功和失败，并保留各目标错误。控制器重启、重复消息、旧执行者迟到上报及重试不得覆盖新一代执行结果或造成跨空间写入。框架失败时已经产生的诊断数据也应尽可能归档，并明确说明采集是否完整。

默认保留时间、选择的目标和数据库模式在提交时形成快照；修改用户默认策略影响之后的任务，避免在执行中悄然改变既有任务含义。针对已有原始结果调整保留时间时，须显式指定该任务并校验权限。

## 验收依据

- `command` 与 `agent_evaluation` 在同一空间运行，各自获得平台生成的 TaskID，且不依赖 AppID。
- 原生 Harbor 任务包可以上传、复用；示例使用用户可在本机构建的预构建环境镜像与 Harbor 适配的 Agent。
- Agent 执行、verifier 调用、框架错误、取消和超时均可观测，结果包含原始完整文件。
- API 支持获取任务与保存状态、读取或下载结果、选择 MinIO/数据库及独立重试保存。
- 覆盖单目标成功、多目标部分失败、重复保存请求、数据库元数据模式依赖 MinIO、原始数据过期等场景。
- 覆盖空间隔离、成员权限、Secret 引用、任务包解包安全及旧执行者上报隔离。
- 注册初始化与已有账号策略接入可用；默认 90 天可改，清理不会删除保存副本或可复用任务包。
- 同步可执行 API 示例、配置和部署说明；注明实际测试证据及尚需真实集群验证的边界。
