# Eruun 当前架构与 Trait 边界

> 状态：Implemented Reference。本文只描述 `main` 已实现的架构与公共声明能力；AI Runtime 目标见 [AI Runtime 愿景](ai-runtime-vision.md)，Draft 文档不得反向作为当前事实源。

## 1. 产品边界

Eruun 当前是 Kubernetes 应用与工作流运行时。它提供 HTTP/gRPC 服务端 API、持久化领域模型、异步 Workflow 执行、Kubernetes 资源调和、运行状态查询、独立 `command` Job，以及通过 `traits.eval` 声明的 Harbor 评测。评测既可独立提交，也可作为 Application 的顶层 `job` 组件执行。Eruun 不包含客户端 CLI；通用 Agent 生命周期、MCP、向量化和 vLLM 专用公共契约仍属于后续方向。

当前架构遵循三条事实边界：

1. MySQL 中的领域记录和 Workflow ownership 是持久化事实源。
2. Redis Streams 或 Kafka 负责消息传输，不取代任务状态和执行租约。
3. Kubernetes 是工作负载运行面；Informer 把观察到的运行状态投影回数据库。

## 2. 四类运行角色

同一 `eruun-server` 二进制通过 `--role` / `ERUUN_ROLE` 选择一种角色。直接运行时默认是 `api`，不存在聚合 `all` 角色。

| 角色 | 当前职责 | 不负责 |
| --- | --- | --- |
| `api` | 提供业务 HTTP/gRPC API、认证授权、请求校验、领域调用、任务创建和评测制品传输 | 不消费 Workflow dispatch，不执行 Kubernetes Job |
| `controller` | Kubernetes 全局观察、组件状态投影、延迟任务和结果/outbox 协调、评测结果目标保存与到期清理 | 不派发 waiting task，不执行业务 Workflow |
| `scheduler` | 认领 waiting task、生成 generation/token、发布 dispatch、回收过期执行租约 | 不运行 Workflow Step，不观察全局组件状态 |
| `worker` | 消费 dispatch、认领数据库租约、执行 Workflow/Job、维护 heartbeat | 不提供业务 API，不拥有全局调度选择权 |

Controller 与 Scheduler 使用不同的 Kubernetes Lease。Worker 不参加这两类 Leader Election；每个 Worker 使用自己的 workload observer 等待资源就绪。

## 3. 数据与依赖所有权

| 依赖 | 当前用途 | 所有权边界 |
| --- | --- | --- |
| MySQL | Application、Component、Workflow、Job、账号、设置和制品记录持久化；Workflow generation/token/lease | 任务状态与执行 ownership 的事实源 |
| Redis | 缓存、应用变更分布式锁、取消信号、延迟通知和默认 Redis Streams 消息 | 不是 Workflow 状态事实源 |
| Kafka | 可选的 dispatch/delay/result 消息后端 | 不能替代 Redis 应用锁或 MySQL lease |
| Kubernetes API | Workload、Service、存储、配置、RBAC、Ingress 等资源 | 实际运行资源的事实源，业务查询主要读取 DB 投影 |

消息交付是 at-least-once。Eruun 使用数据库 generation/token fencing 阻止旧 Worker 覆盖新执行，但对云 API 等外部副作用仍要求调用方或 Provider 提供幂等和补偿。

## 4. Application、Component 与 Workflow

Application 是用户侧部署和权限归属单元，必须属于一个 workspace。Component 描述要生成或执行的能力，Workflow 负责把组件操作组织为步骤。

当前组件类型定义在 `pkg/apiserver/config/consts.go`：

| 类型 | 主要用途 |
| --- | --- |
| `webservice` | 长期运行的无状态服务 |
| `store` | 需要稳定身份或持久化存储的服务 |
| `job` | 一次性 Kubernetes Job |
| `scheduledjob` | Kubernetes CronJob |
| `config` / `secret` | ConfigMap / Secret 资源 |
| `cloudjob` | 引擎内的 Provider/Action 扩展；当前空间业务路径拒绝提交与执行 |

当前 Workflow 支持：

- `StepByStep` 和 `DAG` 两种模式。
- component step 与 approval step。
- 执行、取消、审批、超时、失败清理和终态 callback。
- 应用维度的任务查询、状态和 stages 聚合。
- version update、数据库重置和日志归档等已注册内部 Job。

Workflow 的完整状态、租约和恢复语义见 [Workflow 架构指南](workflow-architecture-guide.md)与[分布式运行时设计](enterprise-distributed-runtime-design.md)。

### 4.1 独立空间 Job

独立任务通过 `/api/v1/jobs` 或对应 gRPC 提交。`type: command` 运行指定镜像和命令；`type: job` + `traits.eval` 使用 Harbor 0.22.0 执行上传的原生任务包，旧 `type: eval` 不再接受。两者属于已授权 workspace，由平台生成 TaskID，不要求 AppID、Component 或占位 Workflow 定义。

API 校验声明并持久化 `WorkflowQueue` waiting task；Scheduler 使用现有 dispatch 和数据库租约派发；Worker 将声明构建为 `JobTask`，复用 `InstantJobCtl` 在空间 namespace 中运行 Kubernetes Job，并通过 `JobInfo` 保存执行明细。这条路径没有第二套任务队列或调度器。

Harbor Runner 在启动评测前认领本次执行，通过内部 HTTP 上报阶段、心跳、进度和终态，并上传完整原始结果。Controller 将已保存的源结果交付到配置的 MinIO/数据库目标并清理到期源数据。评测执行、结果采集和各目标保存有独立状态；重试失败的保存目标不会重新运行评测。具体规格、配置和结果门禁见 [空间 Job 与 Harbor 评测 API](workspace-jobs-api.md)。

## 5. 当前 Trait 契约

公共 Trait 结构定义在 `pkg/apiserver/domain/spec/traits.go`。下表描述引擎中的字段与处理能力；实际可提交范围还受空间授权与任务类型校验约束。

| JSON 字段 | 当前作用 |
| --- | --- |
| `init` | 增加 init container，并允许受限制的嵌套 Traits |
| `sidecar` | 增加 sidecar container，并允许受限制的嵌套 Traits |
| `storage` | 声明 ephemeral、persistent、ConfigMap 或 Secret volume/mount |
| `envs` / `envFrom` | 从静态值、字段、Secret 或 ConfigMap 注入环境变量 |
| `targetWorkEnv` | 写入 Pod `nodeSelector` |
| `resources` | CPU、内存和 `nvidia.com/gpu` request/limit |
| `securityPolicy` | 写入容器级 Kubernetes `securityContext` |
| `probes` | liveness、readiness 和 startup probe |
| `rbac` | 引擎可生成 Kubernetes 身份与 Binding；当前空间业务路径拒绝额外 RBAC |
| `rollout` | Deployment/StatefulSet 更新策略 |
| `ingress` | 生成 Ingress 及路由 |
| `service` | 声明一个或多个 Service |
| `share` | 控制 namespace 内共享资源的调和和生命周期策略 |
| `eval` | 顶层 `job` 的共享 LLM 评测规格；可独立提交或由应用 Workflow 的 `jobType: deploy` 执行，模型是评测对象，harness 是执行条件 |

应用内评测沿用所属 Workflow 的 AppID 和 TaskID，以各 Job 的 `executionKey` 区分状态、结果与保存目标。`eval` 不适用于 webservice、init 或 sidecar，也不与自定义镜像/命令混用；其构建路径独立于下方 workload Trait Processor 顺序。

空间路径拒绝 CloudJob、额外 RBAC、任意 ServiceAccount、host namespace/hostPath/hostPort、跨 namespace 操作及 NodePort/LoadBalancer；Ingress 和存储类也必须符合部署配置。Harbor Runner 使用平台固定且受限的专用身份，不开放任意 Pod 或 ServiceAccount 覆盖。引擎存在相应类型或 Processor 不等于用户获得这些权限，详见 [账号与空间边界](account-auth-workspaces.md)。

### 5.1 Processor 边界

`pkg/apiserver/workflow/traits` 直接读取 `spec.Traits` 的具体字段并调用类型化 Processor，无需运行时注册或反射匹配。按显式顺序处理 workload 变更：storage、envFrom、envs、targetWorkEnv、resources、securityPolicy、probes、RBAC、rollout、init、sidecar、ingress。

- Processor 返回容器、volume、env、probe、resource、ServiceAccount、更新策略或附加 Kubernetes 对象，由框架统一应用。
- 附加对象按 GroupKind/namespace/name 去重；同一身份但内容冲突时失败。
- init 与 sidecar 的嵌套处理排除 init、sidecar、targetWorkEnv 和 rollout；已有非法嵌套检查仍保留。
- 未命名 init/sidecar 使用 `<组件名>-init/sidecar-<从 1 开始的序号>`，超长名称复用稳定哈希限长规则。显式名称保持原值；与主容器或其他容器重名时渲染失败。相同输入重复渲染不再因为随机名称改变 Pod template；已部署的旧随机名称在首次按新规则重建时仍会产生一次名称变更，可能触发 rollout。
- `service` 由 Service 资源生成路径读取；`share` 由资源调和和清理路径读取，不由通用 PodTemplate Processor 处理。

新增 Trait 必须先证明它表达了不能由现有 Trait 组合的稳定能力，并同步 spec、校验、processor/resource builder、测试、示例和专题文档。

## 6. Kubernetes 资源执行

Worker 中的 WorkflowCtl 把 Component/Workflow 计划转换为 JobTask，再由 `pkg/apiserver/event/workflow/job` 中的控制器执行。生成、创建/更新、等待、状态保存和失败清理属于 Job 层职责。

独立 `command` 和带 `traits.eval` 的评测 Job 也由 Worker 启动。已有延迟 Job 则由 Worker 先写入数据库检查点，Controller 在到期后创建对应 Kubernetes Job，并协调结果通知；不能将 Controller 简化为只读观察器。

失败清理区分本次创建的资源与执行前已存在的资源；普通失败回滚不能删除仅观察到的外部资源。RBAC 和共享资源有额外保留边界，具体以 [Workflow Failure Policy](workflow-failure-policy.md) 和 [Share Trait](share-trait.md) 为准。

## 7. API 与权限边界

HTTP 业务路由统一使用 `/api/v1` 前缀。应用、组件、Workflow、版本、状态、日志、文件和 Shell API 注册在 `pkg/apiserver/interfaces/api/applications.go`；账号、空间、独立 Job、设置和编程语言由各自 handler 注册。API 角色同时提供版本化 gRPC v1；两种传输复用 Domain 服务和授权规则，gRPC 不经进程内 HTTP 转发。浏览器 OAuth 和 Runner 内部传输等例外见 [gRPC API](grpc-api.md)。

- 业务 API 使用 Bearer 登录，并通过 workspace 归属和成员角色授权。
- HTTP Handler 与 gRPC adapter 处理传输契约，业务规则进入 Domain Service 或独立 Job 服务；Handler 不直接编排 DB/Kubernetes 写入。
- DTO 与 assembler 负责对外 JSON 和脱敏，Domain model 不直接作为新公共响应结构。
- `rbac` Trait 只描述工作负载的 Kubernetes 身份，不替代 Eruun 平台 API 授权。
- `securityPolicy` 只描述容器级 SecurityContext，不等于网络、Secret、工具或云权限。

账号和空间细节见 [账号与空间](account-auth-workspaces.md)，跨层字段所有权见 [核心模块边界](core-module-boundary-and-cross-layer-contracts.md)。

## 8. 当前能力与 AI 方向的分界

当前 Component、Trait、Workflow 和 CloudJob 是后续 AI Runtime 的基础，但不能据此宣称下列能力已经存在：

- Agent 注册、会话、记忆或独立生命周期 API。
- MCP Server 发现、安装、授权、调用和审计。
- Harbor 之外的通用评测框架接入、向量化或模型部署专用任务。
- HAMi 显存/核心资源、RayService、LeaderWorkerSet 或其他 operator-backed workload。
- 通用托管模型、AI 云 Provider 市场或跨集群调度。

独立 `command` Job、独立与应用 Workflow 内的 Harbor 评测、Runner 阶段协议与结果保存已实现；它们不代表上述完整 AI Runtime 能力。后续方向必须先在 Proposal 中列明当前缺口，完成代码和测试后才能升级为 Current。
