# Eruun 架构文档

## 前言

> 状态：Implemented Reference。本文是架构与 Traits 汇总说明；具体命令、路由和配置参数以当前代码和 `docs/README.md` 的事实速查为准。

Eruun 是一个基于云原生的PaaS工作引擎，以轻量化工作流的方式来描述应用，结构模型基于 **OAM(Open Application Model)**，原生设计的工作流作为核心驱动应用的完整生命周期：初始化资源，创建/更新工作负载，发布事件，监听状态……

Eruun中有两个核心能力：

1.**Traits：可组合的能力原子**

Traits结构将Kubernetes中的Pod，Service,Volume等底层概念抽象化，将存储，容器边车，环境变量，初始化，密钥……以Trait的方式定义，使组件不再依赖复杂的Yaml，而是用组合的方式来构建复杂应用。还提供了“引入模版”功能，能快速创建多个相同形态的新应用（如多套 MySQL）,以此来保证生成的资源可用，无冲突，可追溯。

2.**Workflow:任务驱动的应用生命周期**

每次“部署”“更新”“扩缩容”等操作都被抽象成一条工作流实例：支持并行任务，支持状态一致性，组件之间的依赖，持久化执行记录等……
并在基础设施层使用List_watch模式来维护应用状态的整个生命周期，实时同步应用组件之间的状态。

## Workflow （工作流引擎)

Eruun 工作流引擎是整个应用交付系统的核心组件，负责将声明的应用配置转换为实际运行在 Kubernetes 集群上的资源。它充当了"编排者"的角色，协调多个组件的创建、更新和删除操作，确保应用的正确部署。当前版本要求显式配置外部消息队列，可按部署规模在两种分布式后端之间选择：

1.Redis Streams：适用于中小规模部署，支持任务分发和故障恢复。

2.Kafka：适用于高吞吐、大规模部署场景，支持任务分发和重平衡恢复。

> 服务端进程必须显式选择 `api`、`controller`、`scheduler` 或 `worker` 角色；未指定时只运行 API。职责不由 Deployment 副本数推断，各角色可独立扩缩且不要求奇数副本。
>
> Controller 和 Scheduler 分别使用独立 Kubernetes Lease 选主；Worker 始终从 Redis Streams 或 Kafka 消费。Scheduler 负责 waiting task 派发与数据库 lease reaper，Controller 负责 delay/result/outbox 协调。
>
> generation/token ownership 与数据库 execution lease 是唯一执行协议。消息后端初始化失败时服务直接启动失败，运行期故障通过重试、退避和数据库租约恢复，不切换执行模式。

工作流引擎解决了以下核心问题：

- **资源依赖管理**：确保 ConfigMap、Secret、PVC 等依赖资源先于 Deployment、StatefulSet 创建
- **执行顺序控制**：支持串行和并行两种执行模式，满足不同场景需求
- **状态追踪**：完整记录每个任务和 Job 的执行状态，便于问题排查
- **故障恢复**：支持任务重试、取消和资源清理，保证系统一致性
- **分布式扩展**：支持多实例部署，通过 Redis Streams/Kafka 实现任务分发

工作流引擎借鉴了 OAM (Open Application Model) 的设计思想，支持声明式的工作流定义，这决定了组件编排的顺序：

```json
{
  "workflow": [
    {
      "name": "config-step",
      "mode": "StepByStep", //串形模式，组件按声明顺序依次执行，前一个完成后才执行下一个
      "components": ["config", "secret"]
    },
    {
      "name": "database",
      "mode": "DAG", //并行模式，同一 Step 内的组件并行执行，适合无依赖关系的组件
      "components": ["mysql", "redis"]
    },
    {
      "name": "services",
      "mode": "StepByStep",
      "components": ["backend", "frontend"]
    }
  ]
}
```

任务生命周期由状态机管理,状态分为：

```go
// config/consts.go
const (
    StatusWaiting   Status = "waiting"   // 等待执行
    StatusQueued    Status = "queued"    // 已入队，等待 worker 处理
    StatusRunning   Status = "running"   // 执行中
    StatusWaitingApprove Status = "wait_for_approval" // 暂停等待人工确认
    StatusCompleted Status = "completed" // 执行完成
    StatusFailed    Status = "failed"    // 执行失败
    StatusTimeout   Status = "timeout"   // 执行超时
    StatusCancelled Status = "cancelled" // 已取消
)
```




### 工作流执行流程详解

#### 任务创建与入队

通过 API 触发工作流执行时，系统首先在数据库中创建任务记录，状态设为 `waiting`。这确保了任务的持久化存储，即使系统重启也不会丢失。API 同步返回任务 ID，用户可以通过该 ID 查询任务状态。
任务首先写入数据库，以确保持久化，初始化状态为 `waiting`，API 会同步返回TaskId，可通过TaskId 来追踪Job状态。


#### 固定队列执行流程

工作流固定采用持久化队列执行；`msg-type=redis` 与 `msg-type=kafka` 仅用于选择消息后端。Scheduler 负责发现任务并发布，Worker 从消息队列消费并执行。这种职责分离使系统具备水平扩展能力和故障恢复能力。

Scheduler 在轮询数据库发现 `waiting` 任务后，通过 CAS 创建新的 generation/token 和分发租约，再向 Redis Streams 或 Kafka 发布版本 2 消息。Worker 必须以相同 ownership 将任务认领为 `running` 后才能 ACK。

如果API直接写消息队列，消息队列不支持事务的情况下无法保证任务不丢失；

如果API同时写 DB + 队列的情况下分布式事务复杂，难以保证一致性；

如果只用消息队列存任务，则无法查询任务状态、无法支持取消/重试;

当前工作流先持久化任务再通过消息队列分发，数据库提供可查询的 `waiting/queued/running/completed` 状态与 generation/token ownership。进程退出后，Scheduler lease reaper 只回收 execution lease 已过期且 ownership 完整的 `queued/running` 任务并恢复为 `waiting`；API 通过数据库状态机处理取消，多 Scheduler 实例通过 CAS 避免重复分发。

在审批步骤场景下，任务会进入 `wait_for_approval`，并持久化 `currentStep/approvalPending/pendingApprovalStep` 检查点。即使进程重启后任务被重新调度，也会根据检查点回到审批阶段，不会跳过确认步骤。

Worker 崩溃时，Redis 通过 AutoClaim 重新分配消息，Kafka 通过 Rebalance 重新分配分区。

**队列可用性与容错语义**：

- **启动期 fail-fast**：`msg-type=redis/kafka` 但队列初始化失败时，服务直接启动失败。
- **运行期容错**：分发与消费链路出现短暂故障时，优先使用重试与指数退避机制恢复；达到配置的失败阈值后，Worker 才会退出并等待上层拉起。

#### 分布式 ACK 策略（Pass/Fail）

分发 Worker 采用“**消息不阻塞**”策略：

1. Dispatch 消息解析失败、DB 查询失败或执行失败都会记录日志，并 ACK 消息。
2. 任务成功/失败状态以数据库状态机为准，不依赖消息重试来体现最终结果。
3. 该策略避免单条异常消息阻塞整个消费组（特别是 Redis Streams 的 pending 链路）。






#### Step 与 Priority 执行顺序

工作流由多个 Step 组成，每个 Step 包含一组组件。Step 之间按顺序执行，Step 内部根据执行模式（StepByStep 或 DAG）决定组件的执行方式。同时，每个组件生成的 Job 按优先级分组执行，确保依赖资源（如 ConfigMap、Secret）优先创建。

**优先级说明**：

| 优先级  | 值   | 资源类型                         | 原因                            |
| ------- | ---- | -------------------------------- | ------------------------------- |
| MaxHigh | 0    | ConfigMap, Secret                | 被其他资源引用，必须先创建      |
| High    | 1    | PVC, ServiceAccount, Role        | 工作负载资源可能依赖 |
| Normal  | 10   | Deployment, StatefulSet, Service | 主要工作负载                    |
| Low     | 20   | cleanup_resources               | 显式 Reset Workflow 的资源清理  |

**执行顺序总结**：

1. Step 按声明顺序依次执行
2. StepByStep 模式下，组件逐个执行
3. DAG 模式下，组件并行执行
4. 每个组件的 Job 按优先级分组，高优先级先执行
5. 同一优先级的 Job 并发执行
6. StepByStep 下同优先级遇到失败会立即停止后续 Job；DAG 下同批次 Job 会并行跑完后再汇总失败并终止 Workflow。



备注：

1. Step 的 `mode` 通过 `ParseWorkflowMode` 归一化：空值或未知值都会回退为 `StepByStep`。
2. API 入参中的 `components` 与 `properties.policies` 会先合并再去重，兼容两种组件引用写法。
3. 当 Step 含 `subSteps` 且 `mode=DAG` 时，所有 SubStep 的组件会合并后并行执行（仍遵循 Priority 分桶）。
4. 当 Step 含 `subSteps` 且 `mode=StepByStep` 时，每个 SubStep 会拆成独立执行单元，按 SubStep 声明顺序依次执行。
5. 创建/更新 Workflow 时会校验 Step/SubStep 引用的组件是否存在，不存在会直接拒绝配置。



#### Job 类型

Eruun 在工作流里有两层 Job 类型语义：

1. **组件类型（API 入参）**：`component.type`，用于声明业务组件形态。
2. **执行类型（内部调度）**：`jobTask.JobType`，用于选择具体 Job 控制器与执行逻辑。

| 组件类型（`component.type`） | 主要 Kubernetes 资源 | 常见执行类型（`jobTask.JobType`） |
| ---------------------------- | -------------------- | --------------------------------- |
| `webservice`                 | Deployment + Service | `deploy`、`service_deploy`（以及 traits 衍生资源 Job） |
| `store`                      | StatefulSet + Service | `store_deploy`、`service_deploy`（以及 traits 衍生资源 Job） |
| `config`                     | ConfigMap            | `configmap_deploy` |
| `secret`                     | Secret               | `secret_deploy` |
| `job`                        | Job                  | `instant_job` |
| `scheduledjob`               | CronJob | `scheduled_job` |

> 说明：`service_deploy` 既可由 `traits.service` 生成，也可在未配置 `traits.service` 时由 `properties.ports` 自动推导生成。
> 补充：`webservice/store` 的 `properties.command` 会下沉为主容器 `command`（entrypoint）；为空时沿用镜像默认入口。

##### JobType 与优先级对照表

> 下表描述当前构建器实际分配的优先级；`callback` 不走 Step 内优先级分桶，而是在工作流结束后单独执行。

| 优先级 | 值 | `jobTask.JobType` | 典型来源 |
| ------ | -- | ----------------- | -------- |
| MaxHigh | `0` | `configmap_deploy`、`secret_deploy` | 组件类型为 `config` / `secret` |
| High | `1` | `store_pvc_deploy`、`ingress_deploy`、`service_account_deploy`、`role_deploy`、`role_binding_deploy`、`cluster_role_deploy`、`cluster_role_binding_deploy` | Workload Traits 追加资源（`AdditionalObjects`） |
| Normal | `10` | `deploy`、`store_deploy`、`service_deploy`、`instant_job`、`scheduled_job` | 主工作负载与服务暴露、批处理任务 |
| Low | `20` | `cleanup_resources` | 显式 Reset Workflow 的指定组件资源清理步骤；`/version` 全量清理也会生成该类型 |

Traits 聚合 `AdditionalObjects` 时，以 Kubernetes `GroupKind/namespace/name` 作为资源身份，不依赖对象是否显式设置 `TypeMeta`。不同 Kind 的同名资源会分别保留；完全相同的重复对象会合并；同一资源身份但内容冲突时会直接返回错误，避免静默丢弃后出现缺失资源。



#### 调度 Job 类型

调度相关能力分为“组件级调度”与“工作流级调度”两类：

| 调度类型 | 配置入口 | 产物 | 调度行为 |
| -------- | -------- | ---- | -------- |
| 组件级即时任务 | `component.type=job` | Job | 立即执行；若配置 `properties.startTime`，会先进入 Delay 队列，到点后再创建 Job |
| 组件级定时任务 | `component.type=scheduledjob` + `properties.schedule` | CronJob | 由 Kubernetes CronJob 按 cron 周期触发 Job |
| 工作流级定时触发 | Workflow Schedule（`cron`） | Workflow Task | 由 `workflowScheduleDispatcher` 周期扫描并入队执行工作流 |

**补充规则**：

1. `runPolicy` 归一化后支持 `recreate`、`skip_if_completed`（默认 `skip_if_completed`）。
2. 当前运行时 `runPolicy` 仅在 `batchv1.Job` 路径生效（如 `component.type=job`）；`scheduledjob` 的 CronJob 创建路径不执行该判定。
3. 调度表达式采用 5 字段 cron 语义；输入 6 字段时仅允许 seconds=0，随后归一化为 5 字段。
4. 当 `runPolicy=skip_if_completed` 且同名 Job 仍在运行时，不会直接判定失败；运行时会沿用现有 Job 并继续等待其结果。



#### Workflow 级延时执行（`executeAt`）

`/applications/:appID/workflow/exec` 支持 `executeAt`（Unix 秒）用于延时触发整个 Workflow Task，这与组件级 `properties.startTime`（延时创建 Job）是两套机制。

1. `executeAt < 0` 视为非法请求。
2. `executeAt == 0` 或 `executeAt <= now` 会归一化为立即执行。
3. 任务入库后状态仍为 `waiting`；调度扫描 `WaitingTasks` 时会跳过 `executeAt > now` 的记录，到点后再进入正常分发/执行链路。普通延迟任务在 `waiting -> queued` 前会获取应用锁并复检未完成的 cleanup v2/v3 StatefulSet 迁移栅栏；迁移/恢复任务自身豁免。



#### 延迟执行任务机制（源码实现）

延迟执行主要用于带 `properties.startTime` 的一次性任务（当前主要是 `component.type=job` 场景）。

**触发条件**：

1. 组件类型为 `job`，且 `startTime > now`。
2. 任务构建为 `instant_job`，Job 对象中携带 `eruun.job/startTime` 注解。

**固定队列路径**：

1. `InstantJobCtl` 构造带有 `taskId/executionKey/runGeneration` 完整执行身份的 `DelayJobPayload`，并调用 `EnqueueDelayJob`。
2. 消息写入延迟队列主题：`<msg-channel-prefix>.job.delay`。
3. `DelayDispatcher`（消费组：`job-delay-dispatcher`）读取并按 `executeAt` 排序，未到时间则等待。
4. 到时后先执行 `runPolicy` 判定（`recreate` / `skip_if_completed`），再创建 Kubernetes Job。
5. Kubernetes Job 创建或幂等确认成功后持久化 `result_pending` Outbox；在此之前延迟消息保持未 ACK，重投时按完整执行身份确认同一个 Job，不会重复业务执行。
6. `ResultOutboxDispatcher` 会异步处理 `result_pending`：优先投递结果消息到 `<msg-channel-prefix>.job.result`，必要时回退到 leader 侧本地结果处理。
7. `ResultDispatcher` 或本地结果处理负责等待任务结束并回写 JobInfo（状态、开始/结束时间），成功完成时还会尝试采集 Pod 日志并删除已完成的 Kubernetes Job 资源。
8. 只要 Job 创建已确认且 Outbox 已持久化，延迟消息就会被 ACK；结果跟踪失败不再把 delay item 从头重放。

**当前行为（Delay / Result Queue）**：

1. `EnqueueDelayJob` 仍然是同步依赖，失败会直接返回错误。
2. `ResultQueue` 依赖仍通过启动期 fail-fast 保证在进入运行态前可用；但对已创建成功的 delayed Job，结果跟踪改为基于持久化 Outbox 的异步补偿，不再因为结果队列瞬时失败而重放业务副作用。

**边界说明**：

- `component.type=scheduledjob` 且配置 `properties.schedule` 时，生成的是 Kubernetes CronJob，按 cron 周期执行，不走 Delay Queue。
- 延迟分发消费组名固定为 `job-delay-dispatcher`，与主工作流分发组 `workflow-workers` 解耦。
- `instant_job/scheduled_job` 下发成功后可能短暂处于 `distributed/queued/waiting`，Workflow 会将其视为“已分发成功”，最终结果以后续 JobInfo 回写为准。



#### Workflow 级调度器（Schedule Dispatcher）

系统内置 Workflow 级 cron 触发器（区别于组件级 `scheduledjob`）：

1. `workflowScheduleDispatcher` 按 `workflow-dispatch-poll-interval` 周期扫描启用的工作流调度项。
2. 对命中调度窗口的记录，先用 CAS 更新 `next_run` 以抢占执行权，避免多实例重复触发。
3. 入队前会检查应用是否已有运行中/取消中的工作流任务；若忙碌则本轮跳过。
4. 调度器要求 datastore 支持事务；若当前存储不实现事务接口，会直接返回错误，不执行非事务入队 fallback。
5. 命中调度窗口时，`next_run` 抢占、空闲检查、任务入队、`last_run` 更新会在同一事务内提交，避免部分成功导致状态漂移。



#### 任务取消机制（Cancel Watcher）

Job 执行阶段通过 `workflow/signal` 提供取消信号传播：

1. Worker 运行 Job 前会基于 `taskId` 建立 CancelWatcher，并将可取消上下文传递给 Job 控制器。
2. 取消信号以 Redis 为硬依赖：Worker 无法建立 watcher 时会将 Job 标记为失败；用户/API 取消和应用删除取消会在修改任务状态前确认 Redis cancel backend 可用。
3. 取消标记写入键 `eruun:workflow:cancel:<taskId>`，值为 `cancelled:<reason>`；Watcher 每 1 秒检查一次，默认 TTL 45 秒，`Stop` 不删除取消标记，由 TTL 清理。
4. 同一个 `taskId` 可以有多个 Job watcher 同时观察同一个取消标记；系统不再自动降级到本地内存注册表。
5. 任务模型包含 `cancel_source` 字段，用于区分取消来源：`user` / `system`。
6. Worker 仅在 `status=cancelled && cancel_source=user` 时直接 ACK 并跳过执行，避免用户取消后再次落地作业。
7. 历史任务 `cancel_source` 为空时按系统取消处理，保持滚动升级后的兼容重试能力。



#### Workflow 回调机制（Callback Job）

工作流进入终态（`completed/passed/failed/timeout/reject/cancelled`）后，会触发回调任务：

1. 控制器根据终态映射回调事件（`success/failure/cancelled/timeout/reject`），构造 `jobType=callback` 的内部 Job。
2. 回调支持 `GET/POST/PUT/DELETE`，默认 `POST`；超时时间默认 10 秒（可配置）。
3. 回调响应码非 2xx 视为失败；响应体会截断后记录到 JobInfo，便于排障。
4. Callback Job 不参与 Step 优先级分桶，属于工作流收尾阶段的后置动作。



#### 链路追踪机制（Tracing）

系统基于 OpenTelemetry 提供端到端链路追踪：

1. HTTP 层在启用 tracing 时挂载 `otelgin` 中间件，入口请求自动生成/传播 Trace。
2. Workflow 控制器执行时会创建 `workflow-runner` Span，并打入 `workflow.name`、`workflow.task_id` 等属性。
3. 单个 Job 执行时会创建 `job-runner` Span，记录 `job.name`、`job.type` 等属性，形成父子链路。
4. 运行参数支持 `--enable-tracing` 显式开启；通过标准服务启动入口时，`--auto-tracing` 会在 `--enable-tracing=false` 且配置 Jaeger 或外部队列时自动生效。
5. HTTP 中间件顺序固定为 `otelgin -> request logging`；日志仅在 `SpanContext` 有效时输出 `traceID/spanID`，避免出现全 0 链路字段。



#### 任务观测视图（Status / Stages）

系统提供 `/api/v1/workflow/tasks/:taskID/status` 与 `/api/v1/workflow/tasks/:taskID/stages` 两类聚合视图：

1. Status 视图按组件（`service_name`）聚合 JobInfo，并按优先级合并状态（`failed/timeout/reject` > `cancelled` > `running` > `completed`）。
2. 即使某些组件还未落 JobInfo，也会按 Workflow 定义补齐组件条目（默认 `waiting`，或继承任务终态）。
3. Stages 视图同样按组件聚合，并输出去重后的 `info/error` 消息，便于快速定位阶段性失败点。
4. 当任务主状态仍是 `running` 但全部 Job 已终态时，接口会返回聚合后的终态，避免“假运行中”展示。

审批入口为 `POST /api/v1/workflow/tasks/:taskID/approval`：

1. `action=continue`：任务恢复为 `waiting` 并从下一步骤继续执行。
2. `action=cancel`：复用既有取消链路，任务进入 `cancelled`。



#### 组件日志流（SSE）

系统提供 `GET /applications/:appID/components/:componentName/logs` 作为组件级日志流接口（SSE）。

1. 响应类型为 `text/event-stream`，并附带 `X-Eruun-Pod`、`X-Eruun-Container` 响应头，便于调用方定位日志来源。
2. Pod 选择策略为“优先最新 Ready/Running”；若无 Running，则回退到最新 Completed/Failed Pod，并以非 Follow 方式返回历史日志。
3. 支持可选参数 `container` 指定普通容器；未指定时优先匹配组件主容器名，未命中再回退到第一个普通容器。
4. 仅存在 Pending Pod 时返回 409（`The component is pending scheduling.`）；指定了不存在的容器返回 400；未找到可读容器时返回日志不可用错误。



#### 应用操作类 API 行为（Restart / Stop / Start / Update）

除工作流编排接口外，系统还提供应用维度的操作型 API：

1. `POST /applications/:appID/restart` 用于滚动重启应用工作负载，仅处理 `webservice/store`（Deployment/StatefulSet）；实现方式是补丁写入 `kubectl.kubernetes.io/restartedAt` 注解触发滚动重建。
2. 重启接口响应包含 `taskId/restartedAt/restartedResources/skippedResources/failedResources`；命中共享策略（`default/ignore`，未知策略按 `default`）的组件会跳过重启，`force` 不跳过；`Stopped` 组件始终跳过并保持原状态。
3. 重启成功触发后组件状态标记为 `Restarting`；状态标记写入失败时会先记录失败状态的重启任务，并在响应 `failedResources` 中返回 `ComponentStatus` 明细，不再仅记录日志；后续由 Pod/List-Watch 回写为 `Pending/Running/Failed`，列表查询不会主动把 `Restarting` 纠正为 `Running`；已停止组件需通过 start 恢复。
4. `POST /applications/:appID/stop` 用于停止应用下 Deployment 组件，将 `webservice` 对应 Deployment 的 `spec.replicas` 调整为 `0`，保留组件副本数字段作为历史恢复目标，并将就绪副本数写回为 `0`，状态标记为 `Stopped`。
5. Stop 接口响应包含 `taskId/stoppedAt/stoppedResources/skippedResources/failedResources`；命中共享策略（`default/ignore`，未知策略按 `default`）的组件会跳过停止，`force` 不跳过。
6. `POST /applications/:appID/start` 用于启动应用下已停止的 Deployment 组件，将 `webservice` 对应 Deployment 的 `spec.replicas` 恢复为组件记录中的历史副本数，并将组件状态标记为 `Starting`，等待 Informer 回写 `Running/Failed`；非 `Stopped` 组件会跳过且不改写状态，若已停止组件的历史副本数小于等于 `0`，该资源返回失败明细而不会自动回退到 `1`。
7. Start 接口响应包含 `taskId/startedAt/startedResources/skippedResources/failedResources`；命中共享策略（`default/ignore`，未知策略按 `default`）的组件会跳过启动，`force` 不跳过；若已停止组件对应的 Deployment 已被人工删除或命名空间重建导致缺失，系统视为外部人为干预后的资源缺失，start 不负责兜底重建/Apply，该资源会进入 `skippedResources`，组件状态保持 `Stopped`，需要通过重新部署或人工修复资源后再恢复。
8. `POST /applications/:appID/version` 在 `autoExec=true` 且存在组件变更或资源动作、并且工作流触发成功时，会创建 workflow task；对普通更新/新增组件会将 `updatedComponents + addedComponents` 标记为 `Updating`。若工作流已入队后状态标记写入失败，接口仍返回已创建的 `taskId` 并记录错误，避免客户端重试造成重复执行；当副本就绪后，列表查询会补偿纠正为 `Running`。版本更新会执行选定 workflow 的完整步骤，但 `StatefulSet`、`Service`、`PVC` 在受 Eruun 控制字段归一化后与集群当前状态等价时只标记为已观察，不向 Kubernetes 发送更新请求；`StatefulSet` 不会把 Kubernetes 维护字段或 Pod 稳定默认字段差异视为变化。
9. `PUT /applications/:appID/workflow` 支持 `workflowType`（`workflow/update/test/scan/delivery`）；创建应用时会自动维护更新流程工作流（名称 `<appName>-update-workflow`，别名 `<appID>-update-workflow`）。
10. 版本更新请求支持 `workflowId` 指定自动执行的工作流；未指定时使用默认工作流选择逻辑。
11. 版本更新、直接 workflow 执行、工作流级定时调度、数据库重置、既有应用整体刷新和公共资源清理共用 app-scoped 分布式锁，并在同一应用级临界区内完成空闲/pending 检查与后续写入；已提前创建的普通延迟任务在到点分发前还会在同一锁内复检 pending，cleanup v2/v3 迁移/恢复任务自身可通过。全新应用不获取既有应用锁；显式级联删除整个应用则在同一锁内先取消活跃任务，再有意跳过 pending 恢复栅栏完成终止性删除。锁冲突返回 409（BusinessCode `10031`），锁后端不可用返回 503（BusinessCode `10032`）；历史 cleanup v2/v3 StatefulSet 迁移仍为 pending 时返回 400（BusinessCode `10000`）并提示先通过 `/version` 恢复。若存在运行中任务返回 409（BusinessCode `20007`，`workflow task is running`）；若任务处于取消收敛阶段返回 409（BusinessCode `20008`，`workflow task is cancelling`）。
12. 显式 Reset Workflow 可用普通工作流表达指定组件 reset：第一步配置 `jobType=cleanup_resources` 并引用目标组件；第二步使用常规组件部署步骤。全量 reset 入口已迁移到 `/version` 的 `remove cleanup_all` / `add all` 保留动作。清理步骤会删除组件归属的普通运行资源并等待目标资源消失后，才进入后续部署步骤；standalone PVC 与 ServiceAccount、Role、RoleBinding、ClusterRole、ClusterRoleBinding 永久保留。
13. Eruun 可以为应用自动创建 namespace，但普通应用删除、级联删除和资源清理均不会删除 namespace；现有自动创建 annotations 继续保留，供兼容和审计使用。



#### 失败清理（Cleanup Tracker）

1. Job 运行期间会记录资源追踪信息：`Created`（本次创建）与 `Observed`（已存在/仅观察）。
2. 失败、超时或 panic 触发清理时，只删除本次 `Created` 的普通运行资源，不删除 `Observed` 资源；五类 RBAC 即使属于 `Created` 也永久保留。
3. 该机制保证共享资源与外部预置资源不会被误删，回滚边界限定在“本次执行新建对象”。



### Informer 状态同步机制

Informer 状态同步机制用于实时监听 Kubernetes 资源变化，并将组件运行状态同步到数据库。相比传统轮询方式，Informer 采用 List-Watch 机制，它以事件驱动，状态变更及时同步；减少API Server 请求，降低集群负载

| 组件                  | 文件                                 | 职责                                       |
| --------------------- | ------------------------------------ | ------------------------------------------ |
| `Manager`             | `infrastructure/informer/manager.go` | 管理 Informer 生命周期，注册事件处理器     |
| `ResourceReadyWaiter` | `infrastructure/informer/waiter.go`  | 处理资源事件，通知等待者，同步状态到数据库 |
| `types.go`            | `infrastructure/informer/types.go`   | 定义状态类型、等待条目、状态更新结构       |





#### 状态同步流程




Informer 依赖以下 Labels 来识别和过滤资源，为减少内存消耗，Informer 仅监听带有 `eruun.io/app-id` 标签的 Pod，这样 Informer 不会缓存集群中其他应用的 Pod，显著降低内存占用。

| Label Key                    | 说明     | 示例值                     |
| ---------------------------- | -------- | -------------------------- |
| `eruun.io/app-id`         | 应用 ID  | `1us2dy3a2yhczm8yes6spm88` |
| `eruun.io/component-id`   | 组件 ID  | `1`                        |
| `eruun.io/component-name` | 组件名称 | `nginx`                    |

`app.kubernetes.io/managed-by` 与 `eruun.io/component-name` 的 Label value 会按 Kubernetes 63 字符限制进行规范化和稳定 hash 截断。系统内置的 Pod Label、Service selector、日志/容器查询 selector、清理 selector 使用同一个规范化函数，避免因为 Label 被截断后 Service 找不到 Pod。



#### 等待机制与降级路径

1. Deployment/StatefulSet 默认通过 `ResourceReadyWaiter` 走事件驱动等待就绪（基于 Pod List-Watch）。
2. Informer 未启动或不可用时，自动回退为 2 秒轮询等待，不阻塞主执行链路。
3. Waiter 产生的 `WaitError` 会映射为 Job 状态（如 `timeout`、`cancelled`），保持状态机一致性。
4. 异常原因采集包含 `CrashLoopBackOff`、`ImagePullBackOff`、`ErrImagePull`、`CreateContainerError`、`CreateContainerConfigError`、`OOMKilled`；命中后组件状态判定为 `Failed`。
5. 对 `deploy/store/instant_job/scheduled_job`，Job 启动时会先把组件状态置为 `Pending`（`readyReplicas=0`），再由 Informer 持续回写实时状态。
6. `WaitForComponentReady` 在进入事件等待前会先检查 informer 缓存快照；若已满足期望副本数则直接返回成功，避免“无新事件但已就绪”的超时误判。



#### 组件状态

```go
// config/consts.go
type ComponentStatus string

const (
    ComponentStatusRunning    ComponentStatus = "Running"    // 所有副本就绪
    ComponentStatusPending    ComponentStatus = "Pending"    // 部分副本就绪或等待调度
    ComponentStatusFailed     ComponentStatus = "Failed"     // 存在异常或部署失败
    ComponentStatusUnknown    ComponentStatus = "Unknown"    // 未观测到 Pod 快照
    ComponentStatusNotDeploy  ComponentStatus = "Not Deploy" // 未部署
    ComponentStatusCleaning   ComponentStatus = "Cleaning"   // 清理中
    ComponentStatusUpdating   ComponentStatus = "Updating"   // 更新中
    ComponentStatusRestarting ComponentStatus = "Restarting" // 重启中
    ComponentStatusStarting   ComponentStatus = "Starting"   // 启动中
    ComponentStatusStopped    ComponentStatus = "Stopped"    // 已停止
)
```

**状态计算逻辑**：

| 条件                        | 状态    |
| --------------------------- | ------- |
| `lastAbnormal != ""`        | Failed  |
| `totalReplicas == 0`        | Unknown |
| `readyReplicas >= totalReplicas` | Running |
| 其他（含部分就绪/未就绪）   | Pending |

**状态保护逻辑（数据库同步层）**：

- 组件处于 `Cleaning` 时，Informer 事件不会覆盖状态；当副本归零后转为 `Not Deploy`。
- 组件处于 `Not Deploy` 时，Informer 事件不会回写覆盖该状态。



### 并发控制详解

工作流引擎提供一系列配置，控制 StepByStep 模式下同一优先级内 Job 的最大并发数。

| 参数                       | 默认值 | 作用层级    | 说明                         |
| -------------------------- | ------ | ----------- | ---------------------------- |
| `MaxConcurrentWorkflows`   | 10     | 工作流层    | 同时运行的工作流数量上限     |
| `SequentialMaxConcurrency` | 1      | Job Pool 层 | StepByStep 模式下 Job 并发数 |
| DAG 模式                   | 无限制 | Job Pool 层 | 同优先级 Job 全部并行        |

最大并行 Job 数计算公式

> 最大并行 Job 数 = min(请求数, MaxConcurrentWorkflows) × 每个工作流的同优先级并行 Job 数

**不同场景下的并行 Job 数示例:**

| 场景   | 并发请求 | 执行模式             | 每工作流 Job 数 | 最大并行 Job               |
| ------ | -------- | -------------------- | --------------- | -------------------------- |
| 场景 A | 5        | StepByStep（并发=1） | 3               | 5 × 1 = **5**              |
| 场景 B | 5        | DAG                  | 3               | 5 × 3 = **15**             |
| 场景 C | 10       | DAG                  | 3               | 10 × 3 = **30**            |
| 场景 D | 15       | DAG                  | 3               | 10 × 3 = **30**（5个排队） |
| 场景 E | 10       | StepByStep（并发=2） | 4               | 10 × 2 = **20**            |

**说明**：

- 场景 D 中，由于 `MaxConcurrentWorkflows=10`，超出的 5 个请求会排队等待
- 实际执行时，还需考虑 Priority 分组，只有同优先级的 Job 才会真正并行
- 每个 webservice 组件可能生成多个 Job（Deployment + Service + PVC/Ingress 等）
- 工作流并发槽位获取使用独立 `taskGroupCtx`，不受单个任务错误取消传播影响，避免 `acquire workflow slot: context canceled` 误触发。

```
               [Deployment-web] ────────┼─── 全部完成 
               [Service-api] ───────────┤          │
               [Service-web] ───────────┘          ↓
                                                 结束
```

执行过程：

1. **Step 1** 执行完成后，才开始 **Step 2**
2. Step 2 是 DAG 模式，同优先级的所有 Job 并行执行

#### Worker 弹性配置

以下字段当前存在于运行时配置结构中，但服务端命令行没有暴露对应 flag；如需运行时可调，需要先补充 `config.AddFlags` 与部署环境变量。

| 字段                                   | 默认值 | 说明                                                         | 推荐配置                   |
| -------------------------------------- | ------ | ------------------------------------------------------------ | -------------------------- |
| `WorkerMaxReadFailures`  | 0      | Worker 连续读取失败熔断阈值，0=永不熔断                      | 生产环境建议 0（无限重试） |
| `WorkerMaxClaimFailures` | 0      | Worker 连续 AutoClaim 失败熔断阈值，0=永不熔断（仅 Redis 模式有效） | 生产环境建议 0（无限重试） |
| `WorkerBackoffMin`        | 200ms  | 失败后指数退避最小等待时间                                   | 100ms-500ms                |
| `WorkerBackoffMax`        | 5m     | 失败后指数退避最大等待时间                                   | 1m-10m                     |

> **弹性机制说明**：
>
> - **指数退避**：网络抖动时的自愈重试，等待时间按 `min → min*2 → min*4 → ... → max` 增长
> - **熔断阈值**：持续故障时的保护机制，防止 Worker 空转消耗资源
> - 设置为 0 表示永不熔断，适合高可用场景（推荐）

#### 性能调优

| 场景     | 推荐配置                                                | 说明             |
| -------- | ------------------------------------------------------- | ---------------- |
| 高吞吐量 | `workerReadCount=20`, `maxConcurrentWorkflows=50`       | 增加并发处理能力 |
| 低延迟   | `dispatchPollInterval=1s`, `workerReadBlock=1s`         | 减少轮询间隔     |
| 资源受限 | `maxConcurrentWorkflows=5`, `workerReadCount=3`         | 限制并发避免过载 |
| 长时任务 | `defaultJobTimeout=300s`, `workerAutoClaimMinIdle=360s` | 延长超时时间     |

#### 消息队列选型建议

| 场景                   | 推荐  | 原因                   |
| ---------------------- | ----- | ---------------------- |
| 开发测试               | redis | 与生产同路径，便于提前暴露依赖问题 |
| 中小规模 (<100 任务/s) | redis | 部署简单，延迟低       |
| 大规模 (>100 任务/s)   | kafka | 高吞吐量，强持久化     |
| 已有 Redis 基础设施    | redis | 复用现有资源           |
| 已有 Kafka 基础设施    | kafka | 复用现有资源           |
| 需要消息回溯           | kafka | 支持历史消息重放       |

#### 关键配置约束

1. **workerAutoClaimMinIdle > defaultJobTimeout**：确保任务超时后才被认领
2. **workerStaleInterval < workerAutoClaimMinIdle**：确保定期检查过期任务
3. **Redis maxLen**：根据消息量和内存设置，防止内存溢出
4. **Kafka partitions >= workers**：确保每个 Worker 都能分配到分区
5. **workerMaxReadFailures = 0**：生产环境推荐设为 0，依靠退避机制处理网络抖动，避免误熔断
6. **workerBackoffMax > workerReadBlock**：确保退避时间有意义，避免退避时间过短

#### Kafka 模式特别说明

> **注意**：以下配置在 Kafka 模式下**不生效**，Kafka 依赖原生 Rebalance 机制处理消费者故障：
>
> - `workerAutoClaimMinIdle` - Kafka 无需手动认领超时消息
> - `workerAutoClaimCount` - Kafka 的 `AutoClaim()` 直接返回空
> - `workerMaxClaimFailures` - 因 AutoClaim 不生效，此熔断阈值无意义
>
> 以下配置在 Kafka 模式下**正常生效**：
>
> - `workerMaxReadFailures` - Kafka 读取失败时的熔断保护
> - `workerBackoffMin/Max` - 网络抖动时的指数退避重试

#### 字段详解

| 字段                  | 类型    | 限制 | 默认值 | 说明                        |

### EnvFrom 环境变量批量导入

EnvFrom Trait 用于从 ConfigMap 或 Secret 批量导入所有键值对作为环境变量。对应 Kubernetes 中的 EnvFromSource。

#### 字段详解

| 字段       | 类型   | 限制 | 默认值 | 说明                              |
| ---------- | ------ | ---- | ------ | --------------------------------- |
| type       | string | 必填 | -      | 来源类型：`secret` 或 `configMap` |
| sourceName | string | 必填 | -      | ConfigMap 或 Secret 的资源名称    |

#### 使用示例

##### 从 ConfigMap 批量导入

```json
{
  "envFrom": [
    {
      "type": "configMap",
      "sourceName": "app-config"
    }
  ]
}
```

**生成结果**：

```yaml
envFrom:
  - configMapRef:
      name: app-config
```

假设 ConfigMap `app-config` 内容为：

```yaml
data:
  DATABASE_HOST: mysql.default.svc
  DATABASE_PORT: "3306"
  LOG_FORMAT: json
```

则容器会自动获得三个环境变量：`DATABASE_HOST`、`DATABASE_PORT`、`LOG_FORMAT`。



##### 从 Secret 批量导入

```json
{
  "envFrom": [
    {
      "type": "secret",
      "sourceName": "app-secrets"
    }
  ]
}
```

**生成结果**：

```yaml
envFrom:
  - secretRef:
      name: app-secrets
```

可同时从多个来源导入

```json
{
  "envFrom": [
    {
      "type": "configMap",
      "sourceName": "app-config"
    },
    {
      "type": "secret",
      "sourceName": "app-secrets"
    }
  ]
}
```

**生成结果**：

```yaml
envFrom:
  - configMapRef:
      name: app-config
  - secretRef:
      name: app-secrets
```



#### 注意事项

1. **键名冲突**：如果多个来源有相同的 key，后定义的会覆盖先定义的
2. **资源必须存在**：引用的 ConfigMap/Secret 必须事先存在
3. **与 Envs 配合**：可以同时使用 `envFrom` 批量导入和 `envs` 单独定义
4. **无法选择性导入**：`envFrom` 会导入所有键值对，如需选择性导入请使用 `envs`





### Resources 资源限制

Resources Trait 用于定义容器的计算资源限制，包括 CPU、内存和 GPU。对应Kubernetes中的容器资源请求和限制。GPU需要使用异构中间件来实现。

#### 字段详解

| 字段   | 类型   | 限制 | 默认值 | 说明                              |
| ------ | ------ | ---- | ------ | --------------------------------- |
| cpu    | string | 可选 | -      | CPU 资源，如 `100m`、`0.5`、`2`   |
| memory | string | 可选 | -      | 内存资源，如 `128Mi`、`1Gi`、`2G` |
| gpu    | string | 可选 | -      | GPU 数量，如 `1`、`2`             |

#### 资源单位说明

##### CPU 单位

| 格式 | 说明              | 示例              |
| ---- | ----------------- | ----------------- |
| 小数 | CPU 核心数        | `0.5` = 半个核心  |
| m    | 毫核（1核=1000m） | `500m` = 半个核心 |
| 整数 | CPU 核心数        | `2` = 2个核心     |

##### 内存单位

| 格式 | 说明             | 示例    |
| ---- | ---------------- | ------- |
| Ki   | Kibibyte (1024)  | `512Ki` |
| Mi   | Mebibyte (1024²) | `256Mi` |
| Gi   | Gibibyte (1024³) | `2Gi`   |
| K    | Kilobyte (1000)  | `500K`  |
| M    | Megabyte (1000²) | `256M`  |
| G    | Gigabyte (1000³) | `1G`    |

1. 系统将指定值同时设置为 `requests` 和 `limits`
2. GPU 资源可以使用Gi(显存)来划分，也支持单张显卡调度。因为存在异构显卡的情况，所以推荐使用Gi作为资源分片，通过调度策略来避免显存碎片化。



使用示例

```
{
  "resources": {
    "cpu": "500m",
    "memory": "512Mi"
  }
}
```

**生成结果**：

```
resources:
  requests:
    cpu: 500m
    memory: 512Mi
  limits:
    cpu: 500m
    memory: 512Mi
```



#### 注意事项

1. **格式正确**：资源值必须是有效的 Kubernetes 资源量格式
2. **节点容量**：确保集群节点有足够的资源
3. **GPU 支持**：使用 GPU 需要集群安装相应的设备插件
4. **QoS 等级**：同时设置 requests 和 limits 会使 Pod 获得 `Guaranteed` QoS
5. **嵌套使用**：Resources 可以嵌套在 Init 或 Sidecar 中单独配置



> 在 Kubernetes 中，QoS（Quality of Service）等级决定了当节点资源紧张时，哪些 Pod 会被优先驱逐（evict）。
>
> | QoS 等级   | 条件                                                         | 驱逐优先级         |
> | :--------- | :----------------------------------------------------------- | :----------------- |
> | Guaranteed | 所有容器都设置了 requests 和 limits，且两者相等              | 最低（最后被驱逐） |
> | Burstable  | 至少一个容器设置了 requests 或 limits，但不满足 Guaranteed 条件 | 中等               |
> | BestEffort | 没有设置任何 requests 和 limits                              | 最高（最先被驱逐） |
>
> 资源保障：Kubernetes 会确保 Pod 获得它请求的全部资源
>
> 驱逐保护：当节点内存或 CPU 压力大时，Guaranteed Pod 是最后被驱逐的
>
> 稳定性：适合关键业务应用，如数据库、核心服务

### Storage 存储

Storage Trait 用于将存储卷挂载到容器中，支持多种存储类型。详细文档请[参考](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)

#### **存储类型详解**

| **type**     | **对应 Kubernetes 资源**            | 说明                                                         |
| ------------ | ----------------------------------- | ------------------------------------------------------------ |
| persistent   | PersistentVolumeClaim + VolumeMount | 稳定的存储，使用`PersistentVolumeClaim`卷用于将持久卷(PersistentVolume)挂载到Pod中。这种方式可以为Pod提供一个**稳定的存储方式，不会因为重启/Pod崩溃而丢失容器内持久化存储的文件**。 |
| ephemeral    | emptyDir + VolumeMount              | 临时存储，对于定义了 `emptyDir` 卷的 Pod，在 Pod 被指派到某节点时此卷会被创建。 就像其名称所表示的那样，`emptyDir` 卷最初是空的。尽管 Pod 中的容器挂载 `emptyDir` 卷的路径可能相同也可能不同，但这些容器都可以读写 `emptyDir` 卷中相同的文件。 当 Pod 因为某些原因被从节点上删除时，`emptyDir` 卷中的数据也会被**永久删除**。 |
| ~~hostPath~~ | ~~hostPath + VolumeMount~~          | hostPath 可以让**主机节点文件系统上的文件或目录挂载到Pod中**，比如运行一个需要访问节点级系统组件的容器；让存储在主机系统上的配置文件可以被[静态 Pod](https://kubernetes.io/zh-cn/docs/tasks/configure-pod-container/static-pod/) 以只读方式访问。<br />**这种方式存在许多安全风险，所以系统中不支持。** |
| config       | ConfigMap + VolumeMount 或 EnvFrom  | ConfigMap 对象中存储的数据可以被 `configMap` 类型的卷引用，然后被 Pod 中运行的容器化应用使用。<br />但是：1.你必须先[创建 ConfigMap](https://kubernetes.io/zh-cn/docs/tasks/configure-pod-container/configure-pod-configmap/#create-a-configmap)， 才能使用它。2.ConfigMap 总是以 `readOnly` 的模式挂载。3.某容器以 [`subPath`](https://kubernetes.io/zh-cn/docs/concepts/storage/volumes/#using-subpath) 卷挂载方式使用 ConfigMap 时， 若 ConfigMap 发生变化，此容器将无法接收更新。4.文本数据挂载成文件时采用 UTF-8 字符编码。如果使用其他字符编码形式，可使用 `binaryData` 字段。 |
| secret       | Secret + VolumeMount 或 EnvFrom     | `secret` 卷用来给 Pod 传递敏感信息，例如密码。你可以将 Secret 存储在 Kubernetes API 服务器上，然后以文件的形式挂载到 Pod 中，无需直接与 Kubernetes 耦合。 <br />但是：1.使用前你必须在 Kubernetes API 中创建 Secret。2.Secret 总是以 `readOnly` 的模式挂载。 3.容器以 [`subPath`](https://kubernetes.io/zh-cn/docs/concepts/storage/volumes/#using-subpath) 卷挂载方式使用 Secret 时，将无法接收 Secret 的更新。 |

#### **字段详解**

| 字段       | 类型   | 限制 | 默认值        | 说明                                                         |
| ---------- | ------ | ---- | ------------- | ------------------------------------------------------------ |
| name       | string | 必填 | -             | 存储卷的唯一名称标识符，用于生成 Kubernetes Volume 名称。必须符合 DNS-1123 子域名规范（小写字母、数字、连字符）。 |
| type       | string | 必填 | -             | 存储类型，决定底层 Kubernetes 资源类型。支持的值见上列 [存储类型](#存储类型) 章节。 |
| mountPath  | string | 必填 | `/mnt/<name>` | 容器内挂载路径。若未指定，默认为 `/mnt/<volume-name>`。      |
| subPath    | string | 可选 | `""`          | 挂载 Volume 内的子路径。用于将同一 Volume 的不同子目录挂载到不同位置。 |
| subPathExpr | string | 可选 | `""`        | 挂载 Volume 内需要按环境变量展开的子路径，渲染到 Kubernetes `VolumeMount.SubPathExpr`。与 `subPath` 互斥。 |
| readOnly   | bool   | 可选 | `false`       | 是否以只读模式挂载。设置为 `true` 时容器无法写入该挂载点。   |
| sourceName | string | 可选 | `name`        | 仅用于 ConfigMap/Secret 类型。指定实际 ConfigMap 或 Secret 资源的名称。若为空，则使用 `name` 字段的值。 |
| size       | string | 可选 | `"1Gi"`       | 创建缺失 PVC 时请求的存储容量。格式遵循 Kubernetes 资源量规范（如 `5Gi`、`100Mi`）；同名 PVC 已存在时不更新已有 PVC。 |

持久化存储专用字段，即下列字段仅在`type: "persistent"` 时生效：

| 字段         | 类型   | 限制 | 默认值  | 说明                                                         |
| ------------ | ------ | ---- | ------- | ------------------------------------------------------------ |
| tmpCreate    | bool   | 可选 | `false` | **是否使用模板创建模式**：<br/>• `true`：StatefulSet 通过 `volumeClaimTemplates` 动态创建 PVC，模板名使用 `name` 字段<br/>• `false`：使用 standalone PVC 模式；显式 `claimName` 作为 PVC 名，未填写时使用 `name` |
| claimName    | string | 可选 |         | standalone PVC 名称。仅在 `tmpCreate=false` 时生效；为空时使用 `name` 字段。 |
| storageClass | string | 可选 |         | 创建缺失 PVC 时使用的 StorageClass。同名 PVC 已存在时不更新已有 PVC；为空时使用集群默认 StorageClass。 |
|              |        |      |         |                                                              |

#### **逻辑详解**

1.当 `type="persistent"` 时，系统根据 `tmpCreate` 与 `claimName` 决定 PVC 归属：

1.1 tmpCreate = true（模板创建模式）使用volumeClaimTemplates的方式自动创建PVC

```yaml
volumeClaimTemplates:
  - apiVersion: v1
    kind: PersistentVolumeClaim
    metadata:
      creationTimestamp: null
      name: data
```

添加注解：`eruun.io/pvc-role: template`;Volume 引用动态生成的 PVC 名称;

适用场景：需要为每个应用实例创建独立存储



1.2 tmpCreate = false（standalone PVC 模式）

系统会创建基础 PVC 对象（无特殊注解），PVC 名称优先使用显式 `claimName`，为空时使用 `name` 字段。Volume 引用该 PVC 名称。该 standalone PVC 会参与创建、`/applications/try`、UpdateVersion 阶段的名称合法性校验，但允许同命名空间内多个组件或应用共享同一个 PVC。

部署 standalone PVC 时，如果同名 PVC 不存在，Eruun 会按 `size`、`storageClass` 等配置创建；如果同名 PVC 已存在，Eruun 不更新容量、StorageClass、AccessModes 或其他 spec，直接视为成功。普通 workflow/application cleanup 会保留 standalone PVC；`database-reset` 仍会按显式存储重置语义处理 PVC target。

适用场景：由 Eruun 创建普通 standalone PVC，或复用同名 PVC 且避免更新已有 PVC spec。

##### SubPathExpr 挂载

`subPathExpr` 来源于 PaaS workflow 试玩环境日志目录隔离需求，用于把运行时环境变量交给 Kubernetes 在 Pod 创建时展开。它不能和 `subPath` 同时配置。

```json
{
  "storage": [
    {
      "type": "persistent",
      "name": "logs",
      "claimName": "developer-pvc",
      "mountPath": "/app/log",
      "subPathExpr": "$(TZ)/game/$(INSTANCE_ID)/$(SERVER_NAME)/$(POD_IP)"
    }
  ]
}
```

**生成结果**：

- `subPathExpr` 渲染为 Kubernetes `VolumeMount.SubPathExpr`
- `$(POD_IP)` 等运行时字段由 kubelet 在 Pod 创建时按容器环境变量展开
- 旧版本 Eruun 不支持该字段时，调用方不应提前发送 `subPathExpr`



##### 多容器共享存储

```json
{
  "storage": [
    {
      "type": "persistent",
      "name": "shared-data",
      "mountPath": "/data",
      "TmpCreate": true,
      "size": "5Gi"
    }
  ],
  "init": [
    {
      "name": "init-data",
      "image": "busybox:latest",
      "traits": {
        "storage": [
          {
            "type": "ephemeral",
            "name": "shared-data",
            "mountPath": "/init-data"
          }
        ]
      }
    }
  ],
  "sidecar": [
    {
      "name": "backup",
      "image": "backup-agent:v1",
      "traits": {
        "storage": [
          {
            "type": "ephemeral",
            "name": "shared-data",
            "mountPath": "/backup-source",
            "readOnly": true
          }
        ]
      }
    }
  ]
}
```

**说明**：

- 主容器声明 `type: persistent` 并设置 `TmpCreate: true`，系统创建 PVC

- Init/Sidecar 使用 `type: ephemeral` + 相同的 `name` 声明挂载意图

- 系统会自动去重：同名 Volume 只创建一次，各容器的 VolumeMount 独立配置

- 各容器可使用不同的 `mountPath` 和 `readOnly` 设置

  

> **注意**：如果 Init/Sidecar 也使用 `type: persistent`，由于 `TmpCreate` 默认为 `false`，会尝试创建额外的同名 PVC，导致资源冲突或创建多余对象。



#### 注意事项

1. **名称规范**：`name` 字段必须符合 Kubernetes DNS-1123 子域名规范，系统会自动进行规范化处理（小写化、移除非法字符）

2. **PVC 生命周期**：动态创建的 PVC（`TmpCreate: true`）生命周期与应用绑定，删除应用时需考虑 PVC 清理策略

3. **StorageClass**：确保指定的 StorageClass 在目标集群中存在，否则 PVC 将处于 Pending 状态

4. **SubPath 与空目录**：使用 `subPath` 时，如果子目录不存在，Kubernetes 不会自动创建，可能导致挂载失败

5. **只读模式**：对于 ConfigMap 和 Secret 类型，建议始终设置 `readOnly: true`

6. **Volume 去重**：当多个容器（主容器、Init、Sidecar）声明同名存储时，系统只创建一个 Volume，但各自的 VolumeMount 独立配置

7. **多容器共享存储**：Init/Sidecar 容器共享同一个 standalone PVC 时，可以显式使用相同 `claimName`；系统会按最终 PVC 名在单个组件内去重。仅表达临时挂载意图时可使用 `type: ephemeral`

8. **claimName 字段**：该字段用于指定 `tmpCreate=false` 时的 standalone PVC 名称；为空时使用 `name` 字段，并参与名称合法性校验。standalone PVC 允许共享，不作为独占资源名冲突处理；同名 PVC 已存在时部署阶段不更新其 spec。





### Probes 健康探针

Probes Trait 用于定义容器的健康检查探针，Kubernetes 根据探针结果决定容器的运行状态。

- **LivenessProbe**：存活探针，失败时重启容器
- **ReadinessProbe**：就绪探针，失败时从 Service 摘除
- **StartupProbe**：启动探针，成功前不执行其他探针

#### 字段详解

| 字段                | 类型   | 限制 | 默认值 | 说明                                       |
| ------------------- | ------ | ---- | ------ | ------------------------------------------ |
| type                | string | 必填 | -      | 探针类型：`liveness`/`readiness`/`startup` |
| initialDelaySeconds | int32  | 可选 | 0      | 容器启动后延迟多少秒开始探测               |
| periodSeconds       | int32  | 可选 | 10     | 探测间隔秒数                               |
| timeoutSeconds      | int32  | 可选 | 1      | 探测超时秒数                               |
| failureThreshold    | int32  | 可选 | 3      | 连续失败多少次视为失败                     |
| successThreshold    | int32  | 可选 | 1      | 连续成功多少次视为成功                     |

探测方式（三选一）

| 字段           | 类型     | 说明                  |
| -------------- | -------- | --------------------- |
| exec           | object   | 执行命令探测          |
| exec.command   | []string | 要执行的命令          |
| httpGet        | object   | HTTP GET 探测         |
| httpGet.path   | string   | HTTP 请求路径         |
| httpGet.port   | int      | HTTP 请求端口         |
| httpGet.host   | string   | 主机名（可选）        |
| httpGet.scheme | string   | HTTP 或 HTTPS（可选） |
| tcpSocket      | object   | TCP 端口探测          |
| tcpSocket.port | int      | TCP 端口              |
| tcpSocket.host | string   | 主机名（可选）        |

探针类型说明

| 类型      | 用途                 | 失败后果                     |
| --------- | -------------------- | ---------------------------- |
| liveness  | 检测容器是否存活     | 重启容器                     |
| readiness | 检测容器是否就绪     | 从 Service 端点移除          |
| startup   | 检测应用是否启动完成 | 阻止 liveness/readiness 探测 |



#### 使用示例

##### HTTP 健康检查

```json
{
  "probes": [
    {
      "type": "liveness",
      "httpGet": {
        "path": "/healthz",
        "port": 8080
      },
      "initialDelaySeconds": 30,
      "periodSeconds": 10,
      "timeoutSeconds": 5,
      "failureThreshold": 3
    },
    {
      "type": "readiness",
      "httpGet": {
        "path": "/ready",
        "port": 8080
      },
      "initialDelaySeconds": 5,
      "periodSeconds": 5
    }
  ]
}
```

**生成结果**：

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 3
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 5
```

```json
  "probes": [

      "type": "liveness",
```

```yaml
livenessProbe:
  exec:
    command:
      - cat
      - /tmp/healthy
  initialDelaySeconds: 5
  periodSeconds: 5
```



##### 慢启动应用配置

```json
{
  "probes": [
    {
      "type": "startup",
      "httpGet": {
        "path": "/healthz",
        "port": 8080
      },
      "initialDelaySeconds": 0,
      "periodSeconds": 10,
      "failureThreshold": 30
    },
    {
      "type": "liveness",
      "httpGet": {
        "path": "/healthz",
        "port": 8080
      },
      "periodSeconds": 10
    },
    {
      "type": "readiness",
      "httpGet": {
        "path": "/ready",
        "port": 8080
      },
      "periodSeconds": 5
    }
  ]
}
```

**生成结果**：

```yaml
startupProbe:
  httpGet:
    path: /healthz
    port: 8080
  periodSeconds: 10
  failureThreshold: 30       # 允许最多 300s (30*10s) 完成启动
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  periodSeconds: 10          # startup 成功后才开始执行
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 5           # startup 成功后才开始执行
```

#### 注意事项

1. **单一探测方式**：每个探针只能指定 `exec`、`httpGet`、`tcpSocket` 中的一个
2. **每种类型唯一**：同一组件的每种探针类型只能定义一个
3. **启动探针优先**：配置 `startup` 探针时，其他探针在启动成功前不会执行
4. **合理配置阈值**：根据应用特性合理设置 `initialDelaySeconds` 和 `failureThreshold`
5. **端点可用性**：确保探测端点在容器启动后尽快可用



### Init 初始化容器

Init Trait 用于定义在主容器启动前运行的初始化容器。初始化容器按顺序执行，每个必须成功完成后才会启动下一个。对应 Kubernetes 中的 Pod 的初始化容器。

#### 字段详解

| 字段               | 类型              | 限制 | 默认值 | 说明                                     |
| ------------------ | ----------------- | ---- | ------ | ---------------------------------------- |
| name               | string            | 必填 | -      | 初始化容器名称，如为空则自动生成         |
| image              | string            | 必填 | -      | 初始化容器镜像                           |
| properties         | properties结构体  | 可选 | -      | 容器属性配置                             |
| properties.command | []string          | 可选 | -      | 容器启动命令                             |
| properties.env     | map[string]string | 可选 | -      | 环境变量键值对                           |
| traits             | traits            | 可选 | -      | 嵌套 Traits，支持 storage、envs、envFrom |

1. 系统为每个 Init Trait 创建一个 InitContainer
2. 如果 `name` 为空，自动生成格式为 `<组件名>-init-<随机字符>` 的名称
3. 支持嵌套 Traits（但不能嵌套 init 自身，防止无限循环）
4. 嵌套的 storage/envs/resources 等 Traits 会应用到该初始化容器

#### 使用示例

##### 基础初始化容器

```json
{
  "init": [
    {
      "name": "init-permissions",
      "image": "busybox:latest",
      "properties": {
        "command": ["sh", "-c", "chmod -R 755 /data"],
        "env": {
          "DATA_DIR": "/data"
        }
      }
    }
  ]
}
```

**生成结果**：

- InitContainer 名称：`init-permissions`
- 镜像：`busybox:latest`
- 启动命令：`sh -c "chmod -R 755 /data"`
- 环境变量：`DATA_DIR=/data`
- ImagePullPolicy：`Always`



##### 带存储挂载的初始化容器

```json
{
  "init": [
    {
      "name": "init-data",
      "image": "busybox:latest",
      "properties": {
        "command": ["sh", "-c", "cp /config/* /app/config/"]
      },
      "traits": {
        "storage": [
          {
            "type": "config",
            "name": "app-config",
            "sourceName": "my-configmap",
            "mountPath": "/config",
            "readOnly": true
          },
          {
            "type": "ephemeral",
            "name": "shared-data",
            "mountPath": "/app/config"
          }
        ]
      }
    }
  ]
}
```

**生成结果**：

- InitContainer 名称：`init-data`
- 镜像：`busybox:latest`
- Volume 1：ConfigMap `my-configmap` 挂载到 `/config`（只读）
- Volume 2：EmptyDir `shared-data` 挂载到 `/app/config`
- 用途：将 ConfigMap 内容复制到共享存储供主容器使用

#### 注意事项

1. **镜像必填**：`image` 是必填字段，否则会报错
2. **顺序执行**：多个 Init 容器按数组顺序执行
3. **嵌套限制**：Init 容器的嵌套 Traits 不能包含 `init` 自身
4. **共享存储**：Init 容器可以与主容器共享 Volume，用于数据准备
5. **嵌套 RBAC**：Trait只排除 Init,Sidecar，但是在Init或Sidecar中配置RBAC是无意义的，因为Init与主容器共享ServiceAccount。正确做法应该是在在组件根级别配置 RBAC。



### Sidecar 边车容器

Sidecar Trait 用于定义与主容器并行运行的辅助容器，常用于日志收集、代理、监控等场景。对应 Kubernetes 中的边车容器。

#### 字段详解

| 字段    | 类型              | 限制 | 默认值 | 说明                                                        |
| ------- | ----------------- | ---- | ------ | ----------------------------------------------------------- |
| name    | string            | 必填 | -      | 边车容器名称，如为空则自动生成                              |
| image   | string            | 必填 | -      | 容器镜像                                                    |
| command | []string          | 可选 | -      | 容器启动命令                                                |
| args    | []string          | 可选 | -      | 命令参数                                                    |
| env     | map[string]string | 可选 | -      | 环境变量键值对                                              |
| traits  | traits            | 可选 | -      | 嵌套 Traits，支持 storage、envs、envFrom、probes、resources |

#### 逻辑详解

1. 系统为每个 Sidecar Trait 创建一个额外的 Container
2. 如果 `name` 为空，自动生成格式为 `<组件名>-sidecar-<随机字符>` 的名称
3. 支持嵌套 Traits（但不能嵌套 sidecar 和 init）
4. 边车容器可以有独立的健康探针和资源限制



#### 使用示例

```json
          "cpu": "100m",

}
```

- Container 名称：`fluentd`
- 镜像：`fluent/fluentd:v1.14`
- 环境变量：`FLUENTD_CONF=fluent.conf`
- Volume：EmptyDir `app-logs` 挂载到 `/var/log/app`
- 资源限制：CPU `100m`，内存 `128Mi`
- 用途：收集主容器写入 `/var/log/app` 的日志

### RBAC 权限控制

RBAC Trait 用于创建 Kubernetes RBAC 资源，为组件配置细粒度的权限控制。对应 Kubernetes 中的**ServiceAccount**：服务账户;**Role**：命名空间级角色;**ClusterRole**：集群级角色;**RoleBinding**：命名空间级角色绑定;**ClusterRoleBinding**：集群级角色绑定

#### 字段详解

| 字段                         | 类型              | 限制 | 默认值           | 说明                                |
| ---------------------------- | ----------------- | ---- | ---------------- | ----------------------------------- |
| serviceAccount               | string            | 可选 | `<组件名>-sa`    | ServiceAccount 名称                 |
| namespace                    | string            | 可选 | 组件命名空间     | 资源所在命名空间                    |
| clusterScope                 | bool              | 可选 | `false`          | 是否创建集群级角色                  |
| roleName                     | string            | 可选 | `<sa名>-role`    | Role/ClusterRole 名称               |
| bindingName                  | string            | 可选 | `<sa名>-binding` | RoleBinding/ClusterRoleBinding 名称 |
| serviceAccountLabels         | map[string]string | 可选 | -                | ServiceAccount 标签                 |
| serviceAccountAnnotations    | map[string]string | 可选 | -                | ServiceAccount 注解                 |
| roleLabels                   | map[string]string | 可选 | -                | Role 标签                           |
| bindingLabels                | map[string]string | 可选 | -                | RoleBinding 标签                    |
| automountServiceAccountToken | *bool             | 可选 | -                | 是否自动挂载 SA Token               |
| rules                        | []object          | 必填 | -                | 权限规则列表                        |

**Rules 权限规则**

| 字段            | 类型     | 限制 | 默认值 | 说明                    |
| --------------- | -------- | ---- | ------ | ----------------------- |
| apiGroups       | []string | 可选 | -      | API 组，`""` 表示核心组 |
| resources       | []string | 可选 | -      | 资源类型                |
| resourceNames   | []string | 可选 | -      | 具体资源名称            |
| nonResourceURLs | []string | 可选 | -      | 非资源 URL              |
| verbs           | []string | 必填 | -      | 操作动词                |

**常用 API Groups**

| API Group                   | 包含资源                                                    |
| --------------------------- | ----------------------------------------------------------- |
| `""` (core)                 | pods, services, configmaps, secrets, persistentvolumeclaims |
| `apps`                      | deployments, daemonsets, statefulsets, replicasets          |
| `batch`                     | jobs, cronjobs                                              |
| `networking.k8s.io`         | ingresses, networkpolicies                                  |
| `rbac.authorization.k8s.io` | roles, rolebindings, clusterroles                           |

**常用 Verbs**

| Verb             | 说明         |
| ---------------- | ------------ |
| get              | 读取单个资源 |
| list             | 列出资源     |
| watch            | 监听资源变化 |
| create           | 创建资源     |
| update           | 更新资源     |
| patch            | 部分更新资源 |
| delete           | 删除单个资源 |
| deletecollection | 删除资源集合 |
| `*`              | 所有操作     |



#### 使用示例

##### 只读 Pod 权限

```json
{
  "rbac": [
    {
      "serviceAccount": "pod-reader",
      "rules": [
        {
          "apiGroups": [""],
          "resources": ["pods"],
          "verbs": ["get", "list", "watch"]
        }
      ]
    }
  ]
}
```

- ServiceAccount：`pod-reader`
- Role：`pod-reader-role`（命名空间级）
- RoleBinding：`pod-reader-binding`
- 权限：对 pods 资源的 get/list/watch 操作

```

metadata:
  name: pod-reader

# Role

kind: Role

  name: pod-reader-role

  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]

# RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
subjects:
  - kind: ServiceAccount
    name: pod-reader
roleRef:
  kind: Role
  name: pod-reader-role
  apiGroup: rbac.authorization.k8s.io
```

4. **ServiceAccount 绑定**：第一个 RBAC 策略的 ServiceAccount 会被设置到 Pod
5. **automountServiceAccountToken**：设置为 `false` 可提高安全性
6. **多策略处理**：配置多个 RBAC 策略时，各自创建独立的资源集合





### Ingress 

Ingress Trait 用于创建 Kubernetes Ingress 资源，将外部 HTTP/HTTPS 流量路由到服务。对应 Kubernetes 中的 Ingress，需要安装插件。

> Ingress trait 是当前默认 HTTP 入口表达。若后续需要支持 Gateway API、Istio 或其他网关，应在现有 Ingress 行为之外抽象统一 gateway/service 入口，避免业务配置与单一网关实现强绑定。

#### 字段详解

| 字段             | 类型              | 限制 | 默认值             | 说明                 |
| ---------------- | ----------------- | ---- | ------------------ | -------------------- |
| name             | string            | 可选 | `<组件名>-ingress` | Ingress 资源名称     |
| namespace        | string            | 可选 | 组件命名空间       | Ingress 所在命名空间 |
| hosts            | []string          | 可选 | -                  | 全局主机名列表       |
| label            | map[string]string | 可选 | -                  | 标签                 |
| annotations      | map[string]string | 可选 | -                  | 注解                 |
| ingressClassName | string            | 可选 | -                  | Ingress Class 名称   |
| defaultPathType  | string            | 可选 | `Prefix`           | 默认路径匹配类型     |
| tls              | []object          | 可选 | -                  | TLS 配置             |
| routes           | []object          | 必填 | -                  | 路由规则             |

**TLS 配置**

| 字段       | 类型     | 说明                 |
| ---------- | -------- | -------------------- |
| secretName | string   | TLS 证书 Secret 名称 |
| hosts      | []string | 该证书适用的主机列表 |

**Routes 路由规则**

| 字段                | 类型   | 限制 | 默认值   | 说明                                          |
| ------------------- | ------ | ---- | -------- | --------------------------------------------- |
| path                | string | 可选 | `/`      | URL 路径                                      |
| pathType            | string | 可选 | `Prefix` | 路径类型：Prefix/Exact/ImplementationSpecific |
| host                | string | 可选 | -        | 路由级主机名（覆盖全局 hosts）                |
| backend             | object | 必填 | -        | 后端服务配置                                  |
| backend.serviceName | string | 必填 | -        | 服务名称                                      |
| backend.servicePort | int32  | 可选 | 80       | 服务端口                                      |
| rewrite             | object | 可选 | -        | 路径重写配置                                  |

**Rewrite 重写配置**

| 字段        | 类型   | 说明                                  |
| ----------- | ------ | ------------------------------------- |
| type        | string | 重写类型：replace/regexReplace/prefix |
| match       | string | 匹配模式                              |
| replacement | string | 替换值                                |

#### 使用示例

##### 基础路由

```json
{
  "ingress": [
    {
      "name": "my-app-ingress",
      "ingressClassName": "nginx",
      "routes": [
        {
          "path": "/",
          "backend": {
            "serviceName": "my-app-service",
            "servicePort": 80
          }
        }
      ]
    }
  ]
}
```

**生成结果**：

- Ingress 名称：`my-app-ingress`
- Ingress Class：`nginx`

```yaml
                port:
                  number: 80
```

#### 注意事项

1. **路由必填**：`routes` 至少包含一个路由规则
2. **Ingress Controller**：需要集群中安装相应的 Ingress Controller（如 nginx-ingress）
3. **TLS 证书**：TLS 配置中引用的 Secret 必须存在且包含有效证书
4. **路径类型**：
   - `Prefix`：前缀匹配（默认）
   - `Exact`：精确匹配
   - `ImplementationSpecific`：由 Ingress Controller 决定
5. **注解差异**：不同 Ingress Controller 的注解语法可能不同

> 应该将Ingress和RBAC,SelectNode这种配置统一管理在数据库中，这样在进行配置的时候，可以通过选择不同的场景来适配不同的配置，可以简化数据结构，简化用户的心智。



### Rollout 发布策略（Trait）

`traits.rollout` 用于声明长期运行 workload 的发布/更新策略。它是 workload 级 Trait，只能放在组件顶层，不能放在 `init[].traits` 或 `sidecar[].traits` 中。

#### 映射关系

| 组件类型 | Kubernetes 字段 | 支持类型 |
| -------- | --------------- | -------- |
| webservice | `Deployment.spec.strategy` | `RollingUpdate`、`Recreate` |
| store | `StatefulSet.spec.updateStrategy` | `RollingUpdate`、`OnDelete` |

#### 配置契约

1. 未配置 `traits.rollout` 时，Eruun 不声明 workload strategy；若线上 Deployment 仍残留非默认 strategy，reconcile 会把它重置回默认滚动行为。
2. `webservice` 的 `RollingUpdate` 必须提供 `rollingUpdate.maxSurge` 与 `rollingUpdate.maxUnavailable`，二者不能同时为数值 `0`。
3. `webservice` 的 `Recreate` 不允许提供 `rollingUpdate`。
4. `store` 的 `RollingUpdate` 支持 `partition` 与 `maxUnavailable`；`maxUnavailable` 配置后必须大于 `0`。
5. `store` 的 `OnDelete` 不允许提供 `rollingUpdate`。
6. `IntOrString` 支持非负 JSON 整数或百分比字符串；`"1"`、`"0"` 这类数字字符串会被拒绝，`"00%"`、`"-0%"` 会按数值 `0` 参与 zero guard。

#### 执行链路

1. API validation 先校验 rollout 的组件类型、嵌套位置、策略类型与数值约束。
2. `workflow/traits.RolloutProcessor` 将合法 trait 转换为 Deployment/StatefulSet 的原生 strategy 字段。
3. `GenerateWebService` / `GenerateStoreService` 生成期望 workload，并交给对应 Job Controller。
4. Job Controller 通过幂等比较决定是否 apply；移除 rollout 时，空期望 strategy 表示 Eruun 不再声明该字段。



### Service 服务暴露（Trait）

`traits.service` 用于声明组件要生成的 Service。存在 `traits.service` 时优先按 Trait 生成；未配置时，系统才回退使用 `properties.ports` 推导默认 Service。

#### 字段详解

| 字段 | 类型 | 限制 | 默认值 | 说明 |
| ---- | ---- | ---- | ------ | ---- |
| name | string | 可选 | 组件名 | Service 名称 |
| type | string | 可选 | `internal` | 暴露类型：`internal/node/public/external`（兼容 `ClusterIP/NodePort/LoadBalancer/ExternalName`） |
| headless | bool | 可选 | false | 仅 `internal` 类型可配置为 headless |
| selector | object | 条件必填 | - | 非 `external` 类型必填 |
| externalName | string | 条件必填 | - | `external` 类型必填 |
| labels | object | 可选 | - | Service 标签 |
| ports | array | 必填 | - | Service 端口列表 |

#### 注意事项

1. 一个组件可配置多个 `service` Trait（多 Service）。
2. `ingress` 未显式指定 `serviceName/servicePort` 时，会优先从 `traits.service` 选择后端。
3. `external` 类型不要求 selector，但必须提供 `externalName`。



### Share 共享策略（Trait）

`traits.share` 用于声明组件资源在命名空间范围内的共享策略。策略会下沉到该组件生成的资源标签中（如 Service、Ingress、ConfigMap、Secret、PVC、RBAC 等）。五类 RBAC 即使未配置 `traits.share`，也会自动获得 `strategy=default` 的共享生命周期标签，并采用下述专用调和与清理语义。

| 策略值 | 行为 |
| ------ | ---- |
| `default` | 普通资源已存在同 `eruun.io/share-name` 的对象时跳过创建，不存在则创建/更新；RBAC 始终正常调和 |
| `ignore`  | 普通资源和 RBAC 都直接跳过创建逻辑（Job 状态为 `skipped`） |
| `force`   | 不做共享判断，普通资源和 RBAC 都正常创建/更新 |

**补充说明**：

- `share` 不改变 Workflow Step 编排顺序。
- 对普通资源和 workload 操作，`default/ignore` 会被视为共享组件并跳过对应清理或重启，`force` 不跳过；五类 RBAC 不采用该清理规则，任何 share 策略和清理入口都不会删除。
- 普通资源的 `default` 策略会在共享 List 判断前以 `eruun-share:<kind>:<share-name>` 为粒度加锁；生产路径要求 Redis 分布式锁可用。五类 RBAC 的 `default/force` 不执行共享 List 判断，也不获取该锁。
- RBAC 资源更新前会校验是否为平台托管对象（`app.kubernetes.io/managed-by=eruun` 与 `eruun.io/app-id=<appID>`）；非托管资源仅观察不改写。
- 失败清理阶段只删除本次 `Created` 的普通运行资源，不影响既有共享对象；五类 RBAC 即使属于 `Created` 也永久保留。



### Traits 处理顺序

系统按以下顺序处理 Traits：

1. Storage（存储）
2. EnvFrom（批量环境变量） 
3. Envs（环境变量） 
4. TargetWorkEnv（目标工作环境）
5. Resources（资源限制）
6. SecurityPolicy（安全策略）
7. Probes（健康探针）
8. RBAC（权限控制）
9. Rollout（发布策略）
10. Init（初始化容器）
11. Sidecar（边车容器）
12. Ingress（入口流量）

> 该顺序对应 `workflow/traits` Processor 注册顺序，仅覆盖会直接改写 Workload 的 Trait，不包含 `service/share`。


#### Service 与 Share 的执行阶段

1. `service/share` 在 Workflow Job 构建阶段消费，而非在 Trait Processor 管道中执行。
2. `service` 决定 Service Job 的目标资源与端口映射；缺省时回退 `properties.ports` 自动推导。
3. 普通资源的 `share` 通过 `eruun.io/share-name` 与 `eruun.io/share-strategy` 标签驱动共享判定，并结合锁机制避免并发重复创建；五类 RBAC 的隐式或显式 `default` 不执行共享 List 判断，也不获取该锁。
4. 普通资源命中共享跳过或任一资源配置 `ignore` 后，Job 仍会落库并标记为 `skipped`；RBAC 的 `default/force` Job 正常调和，用于完整追踪工作流执行轨迹。



#### 嵌套 Traits 支持矩阵

| 父 Trait | 可嵌套的 Traits                                         | 排除的 Traits |
| -------- | ------------------------------------------------------- | ------------- |
| Init     | storage, envs, envFrom, resources, securityPolicy, probes, rbac、ingress  | init, sidecar |
| Sidecar  | storage, envs, envFrom, probes, resources, securityPolicy, rbac、ingress | init, sidecar |
